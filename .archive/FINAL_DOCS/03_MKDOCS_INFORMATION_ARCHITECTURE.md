# MkDocs Information Architecture

## Purpose

Define the target `mkdocs.yml` navigation model for a reproducible scientific pipeline and biological database project, using the current repository as the source of truth.

## Design constraints

- preserve the existing root MkDocs setup in `mkdocs.yml`
- expand the site through modular markdown pages
- keep the primary top-level sections compact and predictable
- separate pipeline validation from GX validation
- leave room for versioned releases
- avoid sections that cannot be supported by current code or artifacts

## Why this architecture

### Home

The landing page should explain what BioRemPP is, what is generated, and where each execution surface lives.

### Getting Started

This section should answer:

- what the project requires
- how the environment is set up
- how to execute the shortest correct run

### User Guide

This section should answer operational questions:

- which files must exist
- how to run the modular pipeline
- how to run the monolith
- where outputs appear
- what to do when something fails

### Pipeline Architecture

This section should explain:

- the DAG stages
- the rule modules
- the relationship between rules, scripts, config, and outputs

### Database Reference

This section should act as the data contract and output reference:

- schema
- curated inputs
- analysis artifacts
- provenance semantics

### Pipeline Validation

This section should document validation that is part of the Snakemake runtime itself, especially the reports generated by `30_validation.smk`.

### Data Validation (GX)

This section should document the standalone validator:

- expectation suites
- validation modes
- configuration
- testing
- baseline refresh policy

### Reference

This section should capture stable supporting material:

- data sources
- terminology

### About

This section should handle repository-level governance:

- project scope
- contributing expectations
- release note pointers

## Deliberate exclusions from top-level nav

The old archived navigation included `Interoperability`.
That section should stay out of the first official delivery unless there is verified code and usage documentation to support it.

Reason:

- it is easier to add later than to keep a weak section alive
- the current repository already has enough material for a strong core documentation set without it

## Phase model

### Phase 1 - required for first official publication

- Home
- Getting Started
- User Guide
- Pipeline Architecture
- Database Reference
- Pipeline Validation
- Data Validation (GX)

### Phase 2 - add after core verification is stable

- Reference
- About refinement
- any future interoperability material

## Navigation implementation note

The historical nav in `.archive/docs_deprecated/mkdocs.yml` is the best starting scaffold, but each page title and path in the new docs must still be revalidated against the current repository layout before being copied into root `mkdocs.yml`.
